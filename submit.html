Submission Guidelines

Share your predicted queries and database execution results.

Submit to the leaderboard

To request a leaderboard entry, email your submission archive or a downloadable link to lex2m673@gmail.com. Use the subject [TQTS-Bench Submission] <method name>.

Include a short method description, your preferred display name, and any self-evaluated scores. Submissions are reviewed before leaderboard inclusion; sending an email does not automatically create an entry.

Both are required: the final predicted SQL (or native TSDB query) for each question, and the actual result obtained by executing that query against its benchmark database.

Prepare your files

Predicted queries
Provide the exact final query text in UTF-8. Use SQL where applicable and the database's native query syntax otherwise. Preserve package identifiers and question identifiers from the benchmark release.
Execution results
Provide complete, machine-readable outputs, not screenshots, summaries, or scores alone. CSV is suitable for tabular outputs; JSON is suitable for structured outputs. Preserve column names, values, row order, timestamps and precision. Document types and null encoding; include all result sets when applicable.
Manifest
Map each package and question to its query file and result file. Record execution status, including errors, timeouts, skipped questions and successful empty results. A missing output must not be represented as an empty successful result.
Run description
State the benchmark release or revision, evaluated packages and questions, database versions and relevant settings, model/version, method, prompts, decoding settings, tools, execution timeouts, and any training or tuning on benchmark material. Include commands or scripts needed to reproduce the run where available.
Suggested archive layout 
submission.zip
  README.md
  manifest.jsonl
  queries/
    <package_id>/<question_id>.sql
  results/
    <package_id>/<question_id>.csv

This layout is a suggestion, not an evaluator-specific schema. Use .txt for non-SQL queries and .json for non-tabular results. Your manifest must unambiguously connect every output to the original benchmark question.

Keep evaluation comparable

  • Submit one final prediction and its corresponding execution result per question. If the system generates multiple candidates, describe its automatic selection procedure; do not manually choose answers using reference results.
  • Execute predictions on the benchmark database contents without changing the data to make predictions succeed. Disclose any import transformations, unavailable packages, or other departures from the released setup.
  • Report the full evaluated scope, including failures. Clearly label partial evaluations and their denominator; do not present a subset score as a full-benchmark score.
  • Disclose access to reference queries or answers, manual intervention, and any additional information supplied to the model.

Prepare an anonymous submission

Use a method alias if you wish to remain anonymous. Author names and affiliations are not required in the submission archive. Check file metadata, shared-link names and logs for identifying information.

Do not include credentials, access tokens, private connection strings, internal hostnames or personal filesystem paths. Remove these from configuration and logs without altering query semantics or result values. If required outputs contain sensitive material, contact the submission address before sending them; do not silently redact evaluation results.

No database dumps or source datasets are required. Submit predictions, execution outputs and reproducibility information only.
