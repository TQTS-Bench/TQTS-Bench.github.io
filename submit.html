Submission Guidelines

Share your predicted queries and database execution results.

Submit to the leaderboard

To request a leaderboard entry, email your submission archive or a downloadable link to lex2m673@gmail.com. Use the subject [TQTS-Bench Submission] <method name>.

Include your preferred method display name and a short run description. Self-evaluated scores are optional. Submissions are reviewed before leaderboard inclusion; sending an email does not automatically create an entry.

Both are required: the final predicted query for each question, and the actual output obtained by executing that query against its benchmark database.

Prepare your files

submission.json
Submit one UTF-8 JSON object containing a records array. Each record must identify one benchmark question and contain the prediction and its execution evidence. Use the fields below; separate query files, result files and a manifest are not required.
README.md
State the method display name, model/version, benchmark and data revisions, evaluator revision, intended package/question coverage, execution timeout, and deviations from the released database setup. Briefly describe generation and candidate selection, and disclose reference-answer access, benchmark training/tuning or manual intervention. Detailed prompts, source code, logs and self-evaluated scores are optional.
Existing evaluator users
Run the evaluator with --include-outputs and submit its per-model report, with private paths and credentials removed from metadata and diagnostics. Without this flag, raw execution outputs are omitted. Submit each model's detailed report, not only a multi-model summary.
Preserve runner output
generated_stdout is a JSON string containing the exact output returned by the benchmark runner. Do not convert it to a new table, round numbers, sort rows, rename fields, flatten labels, or discard timestamps or nulls. JSON escaping is lossless; replacing the output with a parsed JSON object is not this format.

Record fields

Question identity
database_id: exact package ID. qa_id: exact question ID from that package. The pair must be unique and must match the declared benchmark revision.
Prediction
generated_query: final query string, without explanatory prose. executed_generated_query: query actually executed after runner transformations, or null if it was not executed.
Execution evidence
generated_stdout and generated_stderr: runner output strings; use "" when captured but empty, and null when not produced. generated_returncode: integer runner return code (0 for success), or null when not executed. Retain any captured partial output on failure.
Time context
evaluation_time: the fixed reference time from the package configuration, not the wall-clock submission time; use null only when the package defines none. Preserve temporal_binding when emitted by the evaluator. Relative-time queries must use the benchmark's reference time and timezone.
Failure information
Include stage and detail for failed, skipped or unexecuted questions, explaining the cause. Use an empty generated_query only if generation produced none. Do not omit failed questions or label a timeout as a successful empty result.
Example JSON structure 
{
  "records": [
    {
      "database_id": "<package ID from the release>",
      "qa_id": "<question ID from that package>",
      "generated_query": "<final query>",
      "executed_generated_query": "<query actually executed>",
      "evaluation_time": "<package reference time, or null>",
      "generated_returncode": 0,
      "generated_stdout": "<exact runner output as a string>",
      "generated_stderr": ""
    }
  ]
}

Replace the illustrative placeholders with real values; use the JSON value null, not the string "null", where applicable. Include one record for every question in the declared scope. Compress the two submission files if needed.

The benchmark supplies reference queries, reference outputs and per-question matching policies. You do not need to submit them. Existing report fields such as gold_query, gold_stdout, match_policy and passed may be retained, but participant-supplied references, policies and scores are not authoritative.

This is an intake format aligned with evaluator report fields, not a new command-line upload mode. The main evaluator generates and executes queries; it does not directly read a submission file. Submissions require validation and review before scoring.

Keep evaluation comparable

  • Submit one final prediction and its corresponding execution result per question. If the system generates multiple candidates, describe its automatic selection procedure; do not manually choose answers using reference results.
  • Execute predictions on the benchmark database contents without changing the data to make predictions succeed. Disclose any import transformations, unavailable packages, or other departures from the released setup.
  • Report the full evaluated scope, including failures. Clearly label partial evaluations and their denominator; do not present a subset score as a full-benchmark score.
  • Disclose access to reference queries or answers, manual intervention, and any additional information supplied to the model.

Prepare an anonymous submission

Use a method alias if you wish to remain anonymous. Author names and affiliations are not required in the submission archive. Check file metadata, shared-link names and logs for identifying information.

Do not include credentials, access tokens, private connection strings, internal hostnames or personal filesystem paths. Remove these from configuration and logs without altering query semantics or result values. If required outputs contain sensitive material, contact the submission address before sending them; do not silently redact evaluation results.

No database dumps or source datasets are required. Submit predictions, execution outputs and reproducibility information only.
